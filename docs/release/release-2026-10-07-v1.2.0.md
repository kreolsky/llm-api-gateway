# Release v1.2.0 — 2026-10-07

2 commits (merges excluded) since v1.1.0. The headline theme is native Anthropic Messages:
a client speaking the Anthropic SDK (Lore's pi-ai harness) can now call `POST /v1/messages`
through the router, with the same keys, model access rules and usage stats as the
OpenAI-compatible endpoints.

# What changed for clients

## Anthropic Messages pass-through

- `POST /v1/messages` accepts native Anthropic Messages requests for models served by an
  `anthropic`-type provider. The router checks the key and model access, rewrites only
  `model`, and forwards the body and the SSE stream byte-for-byte.
- The router key may be sent in `x-api-key` (what the Anthropic SDK does); `Authorization:
  Bearer` still works and wins when both are present.
- Router-made errors on `/v1/messages` are Anthropic-shaped
  (`{"type":"error","error":{"type","message"}}`), so the SDK parses them; a mid-stream
  router failure arrives as an `event: error` frame. Upstream 401/429 keep their real status.
- A model requested over the wrong protocol (an anthropic-type model on
  `/v1/chat/completions`, or an openai-type model on `/v1/messages`) is refused with 400
  `wrong_api`, after the access check.
- Client `anthropic-version` / `anthropic-beta` headers are forwarded on this path; the
  router defaults `anthropic-version: 2023-06-01`.

## Model listing

- `/v1/models` carries `api` per model (`openai-completions` | `anthropic-messages`), so a
  harness knows which endpoint to call.
- The pricing set now always includes `input_cache_write`; `model_info.yaml` accepts a
  `compat` block (pi-ai compat flags), rendered as stored.

## Usage stats

- Rows record cache writes (`cache_write_tokens`); Anthropic usage is extracted for stream
  and non-stream. Cost prices cache writes at `input_cache_write`, falling back to the
  prompt rate. Anthropic `prompt_tokens` = input + cache read + cache write, comparable
  with OpenAI-wire rows.

## Config validation

- Static `headers:` in `providers.yaml` may no longer set `authorization` or `x-api-key`
  (router-owned credentials) — such a config is refused at startup / vetoed on reload.
  Other credential names (e.g. Azure `api-key`) stay allowed.

# Internal (no client-visible change)

- README: use cases, a runnable quick start, a second-instance recipe and a client guide.
- Test config: `deepseek-anthropic` provider + `deepseek-a/flash` model.

# Upgrade actions

- `main`: `443f9d7` → this release's SHA (fast-forward).
- Upgrade via `deploy-server`, code-only: `requirements.txt` and `Dockerfile` are
  unchanged, so rsync `src/` + `docker compose restart` is enough.
- No new env vars.
- Usage DB: additive migration — a `cache_write_tokens INTEGER NOT NULL DEFAULT 0` column
  is added on startup; existing rows read 0.
- Prod configs (edited by hand on the server) — needed only to use the new endpoint:
  - `providers.yaml`: add a provider with `type: anthropic` (e.g. DeepSeek's
    `https://api.deepseek.com/anthropic`).
  - `models.yaml`: add a model on that provider.
  - `user_keys.yaml`: keys with a non-empty `allowed_endpoints` need `/v1/messages`.
  - Check that no provider's static `headers:` sets `authorization` / `x-api-key`, or the
    router refuses to start.
- After deploy: `ssh docker "curl -s localhost:8777/health"` →
  `{"status":"ok","version":"v1.2.0"}`.

# Known limitations

- On `/v1/messages` the `reasoning_effort` policy is advertisement only: nothing is gated
  or injected, and `param` is ignored for anthropic-type models.
- A provider speaks one protocol; a vendor offering both needs two provider entries.
