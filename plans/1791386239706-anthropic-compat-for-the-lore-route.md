# Anthropic compat for the Lore route: adaptive effort on deepseek-a/flash and a compat allow-list

## Decisions

- Context: Lore's harness (pi-ai 0.87.1 inside dsh) drives anthropic-type models through `POST /v1/messages`, choosing the protocol by `/v1/models` `api` and passing the entry's `compat` verbatim into pi-ai. Lore talks to ONE router: the production main router on `ssh docker` (`/home/serge/docker/server-ai-api`, container `server-ai-api-api-1`, host port 8777; the instance Lore's `AI_API_URL` points at). `deepseek-a/flash` exists only there (the ext router's `models.yaml` has no `deepseek-a`). Every measurement and check below is against that router.
- Production config is not in the deploy: `deploy-server` rsyncs `src/` only; on the server `config/` and `.env` are authoritative and per router, and a deploy never touches them. So the compat line ships by a hand edit of the production `config/model_info.yaml` (Order step 2), not by the commit.
- Settled values (read from the production `config/model_info.yaml` on 2026-10-07; the repo is stale): `deepseek-a/flash` has `context_length 524288`, `max_completion_tokens 131072`, `architecture.input_modalities [text, image]`, pricing `prompt 0.00000014`, `completion 0.00000028`, `input_cache_read 0.0000000028` and NO `input_cache_write`. The repo entry (`config/model_info.yaml:87-106`, now 262144 / 32768 / `[text]` / `input_cache_write 0.000000175`) is brought in line with production. Ruling: dropping `input_cache_write` drops the line whose comment records the accepted 1h-cache under-report (`config/model_info.yaml:106`); that sentence moves verbatim into the file header's anthropic checklist. Why: DeepSeek reported `cache_creation_input_tokens: 0` on every probe, so the price has no reader on this model. Cost if wrong: one header comment to move back.
- The consumer's contract, outside this repo (dsh is vendored in the Lore repo): `ANTHROPIC_COMPAT_GATE` at `/Users/serge/Develop/lore-knowledge-creator/vendor/dsh/packages/llm/llm-pi-ai/src/catalog.ts:277` marks each `anthropic-messages` compat key `offer` or `withhold`. dsh refuses three ways, each failing that model's resolution so every Lore turn on it dies: a withheld key (`catalog.ts:566`), an unknown key (`catalog.ts:569`), and a key offered only by ANOTHER protocol, e.g. `supportsDeveloperRole` on an anthropic model (`resolveModelCompat`, `catalog.ts:796`). An allow-list of exactly the anthropic `offer` set closes all three.
- Current behaviour, deepseek-a/flash: no `compat` (comment at `config/model_info.yaml:89`). pi-ai then sends budget thinking (`{"type":"enabled","budget_tokens":N}`, low 2048 / high 16384, `xhigh`/`max` clamped to `high`).
- Measured 2026-10-07 against the production router `/v1/messages`, model `deepseek-a/flash`, non-stream, no tools, prompt "Find all integer solutions of x^2 - 7y^2 = 1 with 0 < x < 10000. Show only the final list.", three runs each, `usage.output_tokens`: `effort_low: 663 669 754`, `effort_high: 879 692 650`, `effort_max: 952 1409 1310` (`thinking: {type: adaptive}` + `output_config.effort`); `budget1024: 670 766 941`, `budget16384: 1064 1071 591` (`thinking: {type: enabled}`). DeepSeek honours `output_config.effort` for `max` and shows no measurable response to `budget_tokens`.
- Also measured, same router and date, with system prompt + one tool + `cache_control` blocks as pi-ai builds them: `{"type":"adaptive","display":"summarized"}` with and without `output_config` → HTTP 200; `{"type":"disabled"}` → 200, no thinking block; no `thinking` param → 200 with thinking; thinking blocks carry signatures; streaming emits `thinking_delta`, `signature_delta`, `input_json_delta`; `anthropic-beta: fine-grained-tool-streaming-2025-05-14,interleaved-thinking-2025-05-14` and no beta header both → 200.
- Decision: `deepseek-a/flash` gets `compat: {forceAdaptiveThinking: true}`. pi-ai then sends `thinking: {type: "adaptive"}` plus `output_config: {effort: <the advertised spelling>}`. `forceAdaptiveThinking` is independent of `supportsMidConvoEffort`: only the latter makes pi-ai send `thinking.block_binding` and mid-conversation `output_config` system messages, which the comment at `config/model_info.yaml:89` keeps off DeepSeek; rewrite that comment to say so.
- Current behaviour, compat vocabulary: `_parse_compat` (`src/core/config_schema.py:327`) keeps ANY string key with a scalar value, for any provider type; `render_capabilities` (`src/core/model_capabilities/render.py:59`) renders it as stored. `compat` is manual-only — no normalizer or other `src/` module writes it — so `model_info.yaml` is its only source.
- Decision (operator ruling, final): the allow-list is exactly dsh's anthropic `offer` set, all seven keys: `forceAdaptiveThinking`, `supportsStrictTools`, `supportsEagerToolInputStreaming`, `supportsCacheControlOnTools`, `supportsTemperature`, `allowEmptySignature`, `supportsLongCacheRetention`. Any other key is warned and dropped, in the style of the non-scalar case at `src/core/config_schema.py:344`. The allow-list constant (a `frozenset` named `ANTHROPIC_COMPAT_KEYS`) carries this comment, verbatim, as four lines:
  INVARIANT: the allow-list is exactly the `offer` set of dsh's ANTHROPIC_COMPAT_GATE (lore-knowledge-creator vendor/dsh/packages/llm/llm-pi-ai/src/catalog.ts) — the router never vetoes an offered key on its own policy; a key present in config works.
  Why: the operator alone decides via config (e.g. 1h cache retention is allowed even though /stat under-reports its writes — accepted, model_info.yaml header).
  Re-diff against that gate whenever Lore bumps its dsh or pi-ai pin.
- Decision, scope: the allow-list applies only to models whose provider has `type: anthropic`; compat on any other type is kept as today. Why: `ANTHROPIC_COMPAT_GATE` is the anthropic-messages gate only, and the operator ruling forbids the router vetoing keys on its own policy.
- Decision, type resolution: a new helper `_resolve_provider_types(models, providers) -> dict[str, str]` maps each model id to its provider's `type`, built once in `parse_config` (`src/core/config_schema.py:492`, where `models` and `providers` are both in scope). A model is left out of the map when `ModelEntry.provider` is None (`src/core/config_schema.py:167`) or its provider is absent from `providers.yaml` (already warned by `_warn_dangling_references`, `src/core/config_schema.py:435`). `_parse_model_info` (`src/core/config_schema.py:380`) takes the map instead of growing its own resolution, and passes the looked-up type through `_normalize_model_info_entry` (`src/core/config_schema.py:356`) into `_parse_compat`. Absent from the map — including an orphan model_info entry (already warned at `src/core/config_schema.py:400`) — means "not anthropic": compat as today. `_parse_model_info` is 41 lines and not in `.claude/baselines/func-length.json`; it must stay ≤50, which is why resolution lives in the helper and the checklist below in its own function.
- Decision, anthropic checklist warning: a new function `_warn_anthropic_checklist(provider_types, model_info)` called from `parse_config` after `_parse_model_info`. It iterates the MODELS whose resolved type is `anthropic` — not the model_info entries — so a model with no model_info entry at all warns for both keys (that is the case where pi-ai silently falls back to a 128k window). For each such model lacking `context_length` or `max_completion_tokens` in its kept model_info entry: one warning per missing key, naming model and key. Soft, never fatal; it runs on every applied reload, which is mtime-triggered (`src/core/config_manager.py:413-416`), so it does not repeat between edits.
- Decision, header of `config/model_info.yaml`: the checklist paragraph (`config/model_info.yaml:39-47`) is rewritten, not just trimmed. It currently says `compat` is "only for real Claude models", gives the example `{forceAdaptiveThinking: true, supportsMidConvoEffort: true}`, and requires "pricing incl. input_cache_write" — all three become false. New content: `compat` is for any anthropic-type model and limited to the seven allow-listed keys (others warned and dropped at load); `forceAdaptiveThinking` is the flag for an upstream that honours `output_config.effort` (DeepSeek does); `input_cache_write` is owed only when the upstream reports cache writes; `context_length` / `max_completion_tokens` are now checked at load. Plus the moved 1h-cache sentence. The per-key compat line in the schema block (`config/model_info.yaml:35-37`) gains "anthropic-type: allow-listed keys only".
- Decision, `CLAUDE.md`: its `compat` sentence ("rendered as stored ... is for real Claude models on anthropic-type providers") becomes false on both counts, so it is edited in the same commit. The evidence gate requires an Observation / Rule / File block with verbatim output from the implementing session: use the red-then-green run of the new test class plus the `/v1/models` jq line from local Validation. New wording: compat is manual-only, rendered as stored for non-anthropic types, and for anthropic-type models filtered to dsh's offered set (see INVARIANT on `ANTHROPIC_COMPAT_KEYS` in `src/core/config_schema.py`) — referenced, not restated.
- Existing tests: `TestModelInfoCompat` (`tests/unit/test_config_manager.py:330`) builds its config on a `type: openai` provider, so all four tests pin the non-anthropic branch, which this change keeps; they stay unchanged and green, and a red one means the type scoping was implemented wrong. `test_compat_rendered_as_stored` (`tests/unit/test_model_service.py:719`) feeds model_info directly, bypassing parsing: unaffected, and it already covers rendering.
- Size: M — one commit; it moves the `/v1/models` compat contract and the config schema. Entanglement medium (config hot-reload path): full `tests/unit/` plus `tests/api/` files touching `/v1/models`. `/review` is mandatory.

## Risks

- Of the three advertised levels only two are measurably distinct today: `low` vs `high` was within noise (663-754 vs 650-879); only `max` separates. Accepted; the levels stay advertised as the operator configured them.
- DeepSeek may later reject `thinking.type: "adaptive"`. Signal: HTTP 400 on every Lore turn on the model; fix: remove the compat line from the production config (hot reload, no deploy).
- A warn-and-drop gate hides a dropped key until someone reads the log. Accepted: the alternative is every Lore turn on that model failing.
- dsh drift: when a Lore dsh/pi-ai bump adds a key to the anthropic `offer` set, the router silently drops it (warning only) until the allow-list is updated; when a key moves to `withhold`, the router keeps serving it and Lore turns die. Signal: a router load warning naming a key the operator just added, or a Lore chat error `sets compat "..."`. The INVARIANT names the dsh file so the re-diff is one grep.
- The production config edit is outside the tree and outside the commit; if it is skipped, `/v1/models` never shows the compat and Lore keeps sending budget thinking with no error. Validation's production check catches it.
- The change is not end-to-end proven until Lore's anthropic route ships (Lore plan `.kilo/plans/anthropic-route-via-router.md` in the Lore repo). Until then acceptance covers the router contract only (`/v1/models` across a hot reload), not what pi-ai puts on the wire.
